# Gemma 4 E2B Express training experiment

This is a local experiment for the smallest Gemma 4 already exercised by the browser demo. It does not replace the demo's model or change Chrome's native Prompt API.

## Prepared artifacts

- `scenario-recipe.json`: importable Unsloth Studio Data Recipe. Its local Gemma 4 26B-A4B teacher creates a four-row preview of structured interface requests and observable success criteria. Increase the preview only after inspecting its output. Candidate requests are not confirmed failures or training answers.
- `failure-seeds.jsonl`: five historical receipts to guide the curriculum. Each records its model, prompt, generated source and observed defect. Cross-model failures are explicitly labelled; successful repairs are not labelled as final failures. None is a positive training target.
- `express-system-prompt.txt`: the historical custom guide used by the earlier baseline, with provenance in `experiment.json`. Current runs use the SDK-generated guide under `output/finetuning/gemma4-e2b/standard-guide/system-prompt.txt` instead.
- `lora-pilot.template.json`: a Studio training request for a 20-step, rank-8 text-only LoRA pilot with a 32,768-token sequence limit. Dataset paths are intentionally empty. Use independently validated training and evaluation files.
- `tokenize-dataset.py`: renders the pinned browser chat template with thinking disabled, verifies its inference prefix, and supplies explicit assistant-only labels. It rejects oversized rows rather than truncating them. Studio must use `format_type: "auto"` to recognize these pretokenized files; generic ChatML and raw-text formatting did not preserve the browser template and completion mask in the installed version.

## Collection and training sequence

1. Complete Studio's first-login setup, import the scenario recipe, validate it and inspect a four-row preview. Check that every required field and option appears in its natural-language request and that the criteria agree with it. Extend toward a 24-row pilot after correcting the recipe. Add a seed-backed, balanced run before scaling; random category sampling alone does not guarantee coverage.
2. Replay the requests against the pinned **browser** E2B model and actual prompt template. Record the first draft before automatic repairs, every later attempt separately, compiler diagnostics, rendered fields, submit payloads, preserved values, timings and model identity. Studio/MLX/GGUF results cannot substitute for the quantized ONNX browser baseline.
3. Use the SDK Express compiler and the full component graph to reject invalid programs. Check content separately: requested fields, reachable submit events, original prices/currencies, surface identity and entered values. For form/action cases, fill actual browser controls and invoke their events. Keep both successful and failing cases with their actual outcomes.
4. Ask the teacher to correct only diagnosed defects. Verify the correction through the same compiler and browser checks. Invalid source can appear as repair input, but must never be an assistant training target. For a simple completion-only dataset, put rejected source and diagnostics inside the user message and use the verified correction as the sole assistant response.
5. Create independent training and evaluation JSONL files with `messages` arrays. Split related scenarios and mutations together to avoid leaking near-duplicates. Mix ordinary working cards/forms with hard cases. Audit complete token lengths against the training limit; do not silently truncate a root line or an action update.
6. Select those local dataset files in the LoRA template and confirm the installed Studio backend supports the chosen E2B checkpoint. Keep thinking disabled and verify tokenizer/chat-template equivalence. Run the bounded pilot, inspect held-out generations and loss, then decide whether the data covers enough distinct failures to scale toward 2,000–5,000 verified rows. Row count alone is not an acceptance criterion.
7. Merge the adapter into a compatible checkpoint, prove text-only ONNX export and q4f16 browser loading, and repeat held-out functional checks before changing the demo pin. GGUF or MLX export alone does not establish browser compatibility. Measure first-pass correctness, input/action integrity, latency and download size against the untouched baseline.

## Independent evaluation

`evaluation/cases.jsonl` and `evaluation/manifest.json` freeze 12 unseen acceptance requests and a separate original shopping regression. They contain expectations, not target DSL, and must never enter training. These are separate from the three validation rows used to report training loss. `build-evaluation.py` checks exact request overlap against the pilot and refuses to overwrite changed benchmark inputs or settings. See [the evaluation workflow](evaluation/README.md).

`run-evaluation.py` saves untouched first-attempt model generations with the canonical SDK prompt, browser template and fixed generation settings. Run it for the pinned base and saved adapter, validate both output files using the existing Nx compiler gate, and use `score-evaluation.py` for paired pass rates, per-category results, latency, fixed cases and regressions. These offline scores cannot replace real browser controls/action/streaming checks. The browser model remains unchanged until those checks pass.

The historical Studio chat-endpoint run returned **base 0/12, adapter 0/12** acceptance, with both failing the shopping regression. A later token audit found that endpoint's prompt length differed from the canonical browser prefix in all 26 calls, so these scores do not establish improvement under the browser prompt. Raw results and the discrepancy remain under `output/finetuning/gemma4-e2b/standard-guide/evaluation-v1/`. The corrected runner sends exact browser token IDs to `/v1/completions`, checks input length, and reruns all baselines. The frozen evaluation requests and compiler/content grader remain unchanged. Keep these acceptance requests out of subsequent training; generate distinct curriculum examples for failure categories.

## Gemma 4 E4B pilot (November 2, 2026)

A first LoRA on the demo's default model, `unsloth/gemma-4-E4B-it` at `4e22d7e59e078e63a14f351efdc5232ed366b621`, trained with `mlx_lm.lora` on a 4-bit MLX conversion rather than Studio. Its inputs and results are under the ignored `output/finetuning/gemma4-e4b/pilot1/`; the adapter and browser export are under `/Volumes/DockerData/models/a2ui-e4b-lora/`.

The training file holds 159 rows (54 view creations, 54 action answers, 51 edits) and the validation file 21, built from 96 fresh scenario seeds. The local Gemma 4 26B-A4B teacher wrote every target through llama-server, the SDK compiler accepted each one, and 12 were rescued by a single-line correction. Rows use the demo's current system prompt and request format, so each is about 7.9k tokens, 7.6k of them prompt. Training masked the prompt: rank 8, scale 2.0, learning rate 1e-4, batch 1, a 12,288-token limit, gradient checkpointing, 160 planned steps at about 55 s each, a checkpoint every 40 steps. Validation loss fell from 0.362 to 0.032 by step 80. The run stopped at step 150 with a Metal out-of-memory error while the browser demo shared the GPU, so the adapter is the step-120 checkpoint, SHA-256 `5cfe14039ee48d79e5a5d4333c10acbfe4e264cdec00662241faec72767fe00b`.

Eight held-out cases, none in the training data (two informational cards, two forms, their two submits and two edits), were run with greedy decoding on MLX: base E4B 4/8, Gemma 4 12B 7/8, 26B-A4B 7/8, and the adapter 8/8, with every fact and currency shown, every input bound, every submit answered in its view with the form kept, and every edit applied in place. Replies take 13–28 s on the Mac against 8–13 s for the base, since the adapter writes complete views. Eight cases are a small sample; this is not a benchmark.

`export-browser-adapter.py` merged the 342 adapted matrices into 300 matrices of the pinned `onnx-community/gemma-4-E4B-it-ONNX` graph (`2b6d2e26a962f70a33da8f7cd81e1afdd8d9cfb2`), after confirming every fp16 base matrix equals the Hugging Face weight; 326 MB of q4f16 weight bytes changed and the graph file is unchanged. The export is served as `e4b-pilot1-5cfe14039ee4` and selected with `?gemmaExport=e4b-pilot1-5cfe14039ee4`. The adapter was trained on 4-bit weights and merged into fp16 ones, so the browser model is an approximation of the one scored above.

Run in Chrome on WebGPU through the demo page with the served export, five first attempts committed without a repair: the Fitting form (99.6 s; three facts, four bound inputs, submit button), its submit (67 s; a Fitting Summary card with all four entered values appended under the form, which kept them), an edit adding an opening-hours line (139 s; the line under the heading, form values and summary card intact), the Aquarium card (70 s; all three facts, no inputs) and the Book delivery form (138 s; four price rows, eight inputs with their starting values and options). The aquarium card also added an empty "Total" label the request never named, which the MLX run of the same case did not, so the q4f16 browser weights do not reproduce the MLX outputs exactly. Prefill of the 7.6k-token prompt accounts for most of each wait. Five requests on one machine are a smoke test, not a benchmark; `browser_verified` stays false in the manifest.

The views it builds are spaced too widely. The catalog defines `gap` and `padding` as 4px steps, and the system prompt says so, but the teacher wrote pixel values (`gap=24`, `padding=24` in most rows), the demo's own lessons showed `gap=12`, and the adapter learned to write 96px gaps. The lessons and examples now say `gap=3`, and `pilot1/train/rescale-spacing.py` rewrites the rows' numbers as steps (24→6, 16→4, 8→2, 4→1) in every turn, with the rows' system prompt refreshed from the demo; all 61 creation targets still compile. The second run, `pilot2`, trains from the base on those rows with pilot 1's settings.

### Pilot 2: spacing fixed, facts dropped (November 3, 2026)

Pilot 2 stopped at step 150 with the same Metal out-of-memory error, this time with Chrome closed and no row above 8.5k tokens, so the trainer's memory grows with the step count and later runs simply stop at 120. Validation loss went 0.367 → 0.035 by step 80, as in pilot 1, and the step-120 adapter is SHA-256 `61976e6d91c28a793e63a2d66f675298283a8c7ba5386b5a476b92bd45049273`. It writes every `gap` and `padding` as a step of 6 or less, so the fix worked. The same eight held-out cases, now run with the demo's current prompt for pilot 1 too, all compile for both adapters, but the compile check hides a regression: pilot 2 lists "Room B, second floor" and three of the four Book Delivery prices as label-only rows, where pilot 1 shows all 14 requested facts. `pilot2/eval/score-all.mts` now counts the facts a request names, including values bound through the data model, and reports the spacing values, so a run is only `OK` when the view shows them all: pilot 1 passes 8/8 with 14/14 facts and half its spacing values still in pixels; pilot 2's step-120 adapter passes 6/8 with 10/14 facts, its step 80 passes 6/8 (an orphaned component and a missing admission price) and its step 40 passes 7/8 with every fact (an invalid `variant` on a Text in one edit). All 61 creation rows in the training file contain every fact their request names, so the drop is training variance rather than a data defect.

The browser run of the pilot-2 export (`e4b-pilot2-61976e6d91c2`, merged and served exactly as pilot 1) confirmed it: the Fitting form (108 s), its submit (71 s, an Appointment Confirmation card with all four entered values under the kept form) and the opening-hours edit (69 s) committed on their first attempts with normal spacing, and the Aquarium card needed a repair turn (142 s; the first draft wrote `shadow="md"`, which the catalog rejects in favour of `shadowStyle`) and again added a stray "Total" label, but the Book Delivery form (126 s) rendered its four price rows as "Atlas / Atlas" and so on, with no amounts. Pilot 2 was therefore not uploaded or deployed.

The third run, `pilot3`, resumes pilot 1's step-120 adapter on the rescaled rows for 40 steps at half the learning rate (5e-5) with a new seed: a spacing refresh of the adapter that keeps its facts, rather than another run from the base. Validation loss on the rescaled rows went 0.045 → 0.047 at step 20 → 0.057 at step 40, and the step-40 adapter is broken: creations degenerate into a repeated `$/</` token until the cap, and edits stop after the `surface` line. The step-20 adapter (SHA-256 prefix `bc9888c385bf`) passes 7/8 with every fact shown and every spacing value a step of 8 or less; its one failure is a missing closing quote on a `fontWeight="bold` argument in the Book Delivery creation, which the demo's single-line repair handles. Pilot 2's own step-40 checkpoint (`d53063f5f606`) is the other candidate: 7/8 with all 14 facts and gaps of 3 and 4, failing one edit by putting `variant="secondary"` on a Text. Both were exported for the browser, where the decision was made.

In Chrome, pilot 3's step-20 export built the Fitting form (103 s) and answered its submit (69 s) on first attempts, but the opening-hours edit failed all three attempts (310 s in total): each draft added the new line to root and then replayed the earlier submit answer after it, whose old root left the new label orphaned. Pilot 2's step-40 export (`e4b-pilot2s40-d53063f5f606`) committed all five requests on their first attempts with every fact and price shown and gaps of 3 to 6: the Fitting form (96 s), its submit (68 s, an Appointment Summary with the four entered values under the kept form), the edit (81 s), the Book Delivery form (117 s, four price rows with amounts and eight inputs) and the Aquarium card (81 s, no stray label). It is the selected fine-tune: `TARGET_EXPORT_ID` in `model-identity.ts`, the Firebase packaging script and the deployment notices now name it, and `stage-hub-model.py` assembles its Hugging Face repository (`wolfmanfx/gemma-4-E4B-it-A2UI-Express-ONNX`) from the export, the `mlx_lm` adapter, the system guide and the notices. Pilot 1, pilot 2's step 120 and pilot 3 stay on the model disk as comparisons.

### E2B on the same recipe (November 3, 2026)

To see whether the corrected rows help the smaller model too, `output/finetuning/gemma4-e2b/mlx1/lora.yaml` trains `unsloth/gemma-4-E2B-it` (a 4-bit `mlx_lm.convert` of the base, group size 64, on the model disk) with pilot 2's settings on the same rescaled rows. The plain `mlx_lm.lora` run died with the Metal error `Insufficient Memory` after a varying number of steps (36 to 39 twice from the base, 21 to 24 and then 6 to 9 when resumed from its step-20 checkpoint), with the allocator cache cleared every step, the wired limit raised to the recommended 51 GB and no row longer than 8.5k tokens. A memory poll showed each step's active memory climbing to 46 GB with a 50.9 GB peak, right at that limit, so any slightly larger allocation fails. The 262k-vocabulary logits of an 8k-token row looked like the cause, as Unsloth Studio's E2B run had used cut cross-entropy, but chunking the head only saved about 5 GB: `mlx1/train-chunked-ce.py` runs the stock trainer with a loss that applies the tied-embedding head and cross-entropy per 512-position chunk inside `mx.checkpoint`, skips the masked prompt positions, and disables the trainer's step compilation (a compiled step can neither read the lengths nor split the chunks into separate GPU command buffers, which Metal's watchdog killed). `mlx1/check-chunked-ce.py` shows it computes the same loss and gradient norm as the default loss on a training row. The peak is attention and activation recompute over 8k tokens, so the run is still near the limit, but with that headroom it completed all 120 steps: validation loss 0.484 → 0.054 at step 40, 0.043 at step 80 and 0.029 at step 120, with checkpoints every 20 steps under `/Volumes/DockerData/models/a2ui-e2b-lora/mlx1-chunkedce/`.

On the eight held-out cases with the demo's current prompt, the deployed round-2 Studio adapter passes 4/8: it builds all four views with every fact and gap=5, but both submits rewrite the form and leave an input orphaned, and both edits open a duplicate view instead of updating view-1, which is the weakness the demo README already describes. The new step-120 adapter passes 7/8: both submits answer in view-1 with the form kept and every value shown, both edits apply in place, the three compiled creations show all 11 of their facts with gaps of 2 and 6, and the aquarium card fails on invented syntax (`heading_color = color.primary` and an unquoted `color=color.secondary`). The step-100 checkpoint passes all 8 with all 14 facts, every input bound, both submits and edits in view-1 and gaps of 1 to 6, so it is the E2B candidate. The retrain therefore fixes the follow-up turns that round 2 got wrong and keeps the spacing in steps; the step-120 slip is syntax, which the demo's repair turns address, rather than dropped facts.

`export-browser-adapter.py` merged the step-100 adapter (SHA-256 prefix `eff96be9f058`) into the pinned E2B graph: `mlx_lm` adapts every projection including the per-layer input gates, 275 logical matrices and 240 ONNX matrices against the Studio adapters' 205 and 170, so `exportBase` and the file server now expect 240 for `e2b-` ids and keep 170 for the `round…` ids. Served as `e2b-mlx1s100-eff96be9f058` and run in Chrome with the same five requests as the E4B candidates, it committed all five on their first attempts: the Fitting form (51 s), its submit (39 s, an Appointment Summary with the four entered values under the kept form), the opening-hours edit (72 s; it rewrites the whole view rather than patching it, with the values and summary intact), the Book Delivery form (66 s, the four amounts in one price row and eight inputs) and the Aquarium card (38 s, three captioned facts, no stray label), with gaps of 1 to 4. The 3.1 GB export answers in roughly half the E4B export's time. `stage-hub-model.py` assembled its repository directory from the export, the step-100 adapter, the shared system guide and the card, training settings and notice under `output/finetuning/gemma4-e2b/mlx1/hub/`; it was uploaded to `wolfmanfx/gemma-4-E2B-it-A2UI-Express-ONNX`, whose head now holds it while the round-2 export stays at its earlier revision. The demo's selector offers it as the second fine-tuned mode (`e2b-mlx1s100-eff96be9f058`, loaded from that pinned revision on the public site); the default stays the E4B adapter.
